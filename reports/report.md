## 二、评测体系：先造尺子，再谈优化

官方 scorer 不可见、单次方差约 ±8 分，且一次 smoke 成本高。因此我们自建了三层本地尺子，形成「本地快速迭代 → 官方季度验收」的双轨。

### 2.1 三层本地评测集

| 层 | 数据集 | 规模 | 作用 | 位置 |
|---|---|---|---|---|
| 回归集 | `eval_set.json` | 19 题 / 9 能力维度 | 单用户完整病史（右膝病程），逐题比对 hit@1/5/10/20、MRR、coverage@10 | `/workspace/amc_eval/eval_set.json` |
| 鲁棒集 | `robustness/sets/eval_v2.json` + `para_v2.json` + `neg_v2.json` | 16 核心 + 38 口语改写 + 5 负样本 | 抗改写、抗"看似相关实则无关"的捏造 | `/workspace/amc_eval/robustness/` |
| 规模压力台 | 注入近邻 + 合成干扰 | ×1 / ×8 / ×26 三档 | 记忆量放大后的召回保持率（retention@10） | `robustness/results/s0~s3_*.json` |

回归集刻意设计为**内容正则判分**（不依赖记忆 id），因此两个不同库、不同分块策略也能公平比对；每题标注了"全库仅 2 条命中"这类区分度说明，避免题目本身太容易。

### 2.2 评测器可信度（先验证尺子，再用尺子）

同一个库、同一份代码的两个独立服务臂（8031 / 8040）跑同一套 19 题，**逐项结果完全一致**：

| 指标 | 臂 A | 臂 B |
|---|---|---|
| hit@1 | 0.737 | 0.737 |
| hit@5 | 0.842 | 0.842 |
| hit@20 | 0.895 | 0.895 |
| MRR | 0.7858 | 0.7858 |
| coverage@10 | 1.000 | 1.000 |

> 踩坑记录：向量库目录名不一致（`qdrant_storage` vs `qdrant`）会让检索静默退化为纯 BM25，表现为 hit@1 掉到 0.63。该问题已修复并写入 MANIFEST，避免后续误判。

### 2.3 规模压力台结果（记忆量放大的真实代价）

| 臂 | 干扰注入 | hit@1 | hit@10 | MRR | retention@10 |
|---|---|---|---|---|---|
| s0 原始库 | 无 | **0.737** | 0.842 | 0.7858 | — |
| s1 轻度放大 | 近邻 + 合成 | 0.632 | 0.895 | 0.7228 | 0.574 |
| s2 中度放大 | 更多干扰 | 0.579 | 0.895 | 0.6724 | 0.479 |
| s3 重度放大 | 近邻 5000 条 | 0.526 | 0.789 | 0.6335 | 0.358 |

**读法**：top10 命中率几乎不掉（0.842 → 0.789），但 **top1 命中从 0.737 掉到 0.526**——记忆量放大后"找得到"仍然成立，"排第一"明显变难。这正是后续提高召回深度（P5）与精排质量的直接动机。

### 2.4 抗改写与安全性

| 测试 | 结果 |
|---|---|
| 38 条口语改写（同一事实换说法） | hit@1 0.368~0.395，hit@5 0.684~0.789，hit@10 0.711~0.842 |

## 四、Pipeline 设计

### 4.1 总体结构

```
写入侧（/add）                           检索侧（/search, top_k=100）
──────────────────────────────────       ─────────────────────────────────────────
幂等去重（request_id, SQLite）            ① 查询分析（意图/时间/实体/是否摘要）
   ↓                                      ② 向量召回（bge-m3, 1024d, Qdrant）
分块（消息级 / 会话级, 150~250 词）        ③ BM25 关键词召回（按 user 懒构建）
   ↓                                      ④ RRF 融合
分类（类型/实体/时间表达式）               ⑤ 治理：新值覆盖、去重、重要度
   ↓                                      ⑥ LLM 精排（0~10 分，硬打分）
原子事实抽取（含相对时间归一化）           ⑦ 业务加权：事实优先、选项重合、时效/时序锚
   ↓                                      ⑧ 多样性裁剪（同 session 上限）
摘要层（会话级压缩，可选门控）             ⑨ 预算裁剪 → 返回 ≤ top_k
   ↓
SQLite（元数据/幂等）+ Qdrant（向量）+ BM25 索引
```

### 4.2 关键设计取舍

| 设计 | 选择 | 理由 |
|---|---|---|
| 记忆单元 | 分块 **+ 原子事实** 双写 | 分块保上下文完整，事实保精确命中与时间推理 |
| 检索 | 向量 + BM25 → RRF 融合 | 单一通道在专名/数字/中文场景系统性漏召 |
| 精排 | LLM 硬打分（0~10），`final = 0.7×精排 + 0.3×检索侧` | 排序质量提升明确；失败时 fail-open 退化，不阻塞应答 |
| 时间 | 写入侧归一化相对时间（"上周三"→绝对日期） | 时序题靠排序无法补救"根本没存对时间" |
| 治理 | 新值覆盖旧值、矛盾保留双证据 | 对应官方 D1/D2 能力项 |
| 服务形态 | FastAPI + Qdrant + SQLite，契约严格按官方三接口 | 评测只认接口语义，不改契约 |

### 4.3 单点依赖与资源

- LLM：外部网关（`ecloud.10086.cn` 智能体网关，模型 `qwen3.7-max`），抖动 0.2s~70s，会返回 429。
- Embedding：bge-m3，本机 CPU（8080），640 核共享。
- 存储：Qdrant 本地目录 + SQLite 单文件，均可整库拷贝/回滚。

| 时间 | 事件 |
|---|---|
| 10-29 06:18~06:48 | 基线 smoke，**74.77** |

### 5.2 本轮改造与"官方口径"的边界

- 官方契约只规定三接口语义与 `top_k=100`，**不规定** LLM 并发数、精排批大小、超时时间。这些全部是我们自己的客户端参数，改动不影响契约合规。
- `LLM_MAX_CONCURRENCY`（3→9→6）是纯节流阀，**对分数无影响**，只影响排队与 429 概率。
- `RERANK_BATCH_SIZE=12` 是 P1-2 实验定稿值（已否决 24/24 与 40/20），保持不动。
- 我们坚持的纪律：**不在 smoke query 上做特判**、不改 `top_k` 契约、不估分不编分。

## 九、Full 提交方案（建议）

### 9.1 一句话

**沿用当前 v5 单套代码（自研 pipeline），用「深度召回 + 滑窗精排 + 摘要/治理层」保质量，用「限流 + 超时 + 熔断 + fail-open」保稳定，用「冻结基线 + 独立库」保回滚。**

### 9.2 质量侧配置

| 项 | 取值 | 说明 |
|---|---|---|
| 召回深度 | `RECALL_DEPTH_MAX=120`，实际 `recall_k=min(top_k,120)` | 官方 top_k=100 → 召回 100、精排 100 |
| 精排 | `RERANK_MODE=hard`，批 12，每候选 800 字滑窗 | 兼顾质量与单请求体积 |
| 融合 | `0.7×精排 + 0.3×检索侧` | 精排失败自动退化为融合分 |
| 摘要 | 摘要层开启，按意图门控 | F1 依赖此项 |
| 陷阱抑制 | 开启 | G2 |

### 9.3 稳定侧配置

| 项 | 取值 | 作用 |
|---|---|---|
| `LLM_MAX_CONCURRENCY` | 6 | 低于实测安全线（8 并发 0 次 429），留余量给官方突发 |
| `RERANK_TIMEOUT_SECONDS` | 90 | 覆盖排队，避免整批误判 |
| `RERANK_TOTAL_TIMEOUT_SECONDS` | 180 | 单次检索墙钟上限 |
| 重试 | 4 次 / 预算 25s | 抖动兜底 |
| 熔断 | 20 次失败 / 30s 冷却 | 避免连锁熔断 |
| 降级 | 精排失败 → 融合分；事实抽取失败 → 仅分块 | 永不因 LLM 故障返回 5xx |

### 9.4 回滚与观测

- 8000 端口一键切回 `baseline_74_77` + `baseline_store_74_77`（74.77 冻结快照，SHA256 校验）。
- 全链路 `api_io.jsonl` 记录输入/输出，窗口结束后可直接统计 429/超时/降级次数。
- 每次改造必须满足：本地回归集逐项 diff = 0，或增益项可解释。

### 9.5 明确不做

1. 不针对 smoke 的具体 query 做特判或硬编码。
2. 不修改官方契约（`top_k`、返回结构、状态码）。
3. 不在没有 A/B 证据的情况下调整精排批大小或候选池。
4. 不为了延迟牺牲质量（用户明确要求"质量为第一标准"）。

### 9.6 风险对冲（可选，不阻塞主线）

本机有 **2× 昇腾 910（各 64GB HBM）**，已装 vLLM/torch_npu/CANN。若把 LLM 换成**本地 vLLM + Qwen3**，可彻底消除网关抖动与 429：

- 收益：尾延迟可控、无配额、无跨网关抖动。
- 成本/风险：NPU 当前被另一训练任务占用（余量约 40~50GB）；32B BF16 单卡放不下，需量化；换后端后 smoke 分数**不可与历史横向比较**。
- 建议：作为**并行臂**离线对照精排分数，达标后再切 8000，不在 full 前夜做切换。

## 十、需要领导决策 / 支持的事项

1. **是否批准在近期用掉 1~2 次 smoke** 来验收 P2/P3/P5（当前仅有本地证据，官方分数未验证）。
2. **Full 提交时间窗**与可用的 smoke 次数（剩余约 2 天、约 15 次）。
3. **是否投入 NPU + vLLM 本地化**作为网关抖动对冲（需要确认 NPU 占用可让出、权重可下载）。
4. 若 full 分数不达预期，**是否接受"以 74.77 冻结基线提交"**作为兜底方案。
